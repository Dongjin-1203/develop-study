# TCP 소켓 학습 정리 (2026-11-13)

## 1. 오늘 한 것
- 기본 `socket` 라이브러리로 서버(`server.py`)와 클라이언트(`client.py`)를 따로 실행해 문자열을 주고받음
- 연결 → 대기 → 송수신 → 종료 흐름을 직접 확인
- 학습 계획: 기본 socket → (이후) Flask 등 라이브러리로 확장해 백엔드 지식 쌓기

## 2. 핵심 개념

| 개념 | 설명 |
|---|---|
| 소켓 | 프로그램이 OS의 네트워크 기능을 쓰는 출입구(endpoint). 송수신은 연결된 소켓(`conn`)으로 함 |
| TCP | 연결 지향, 순서 보장, 재전송. **바이트 스트림**이라 메시지 경계가 없음 |
| IP / 포트 | IP는 어느 컴퓨터인지, 포트는 그 컴퓨터의 어느 프로그램인지. 테스트는 `127.0.0.1`(루프백) 사용 |
| 리스닝 소켓 vs 통신 소켓 | 리스닝 소켓(`s`)은 연결 요청만 받는 문, `accept`가 반환하는 `conn`은 해당 클라이언트 전용 소켓 |
| 블로킹 | `accept`, `recv`는 상대가 올 때까지 멈춰서 기다림. 서버가 멈춰 있는 것이 정상 |
| 3-way handshake | `connect` 시 OS가 SYN → SYN-ACK → ACK로 연결을 맺음 (코드에는 `connect` 한 줄로 보임) |

## 3. 서버 흐름과 함수

| 순서 | 함수 | 역할 | 비고 |
|---|---|---|---|
| 1 | `socket.socket(AF_INET, SOCK_STREAM)` | IPv4/TCP 소켓 생성 | |
| 2 | `bind((host, port))` | 소켓에 IP와 포트를 묶음 (서버의 고정 주소 정하기) | 인자는 **튜플 하나** |
| 3 | `listen([backlog])` | 연결 요청을 받는 상태로 전환 | 바로 반환됨. backlog는 선택 |
| 4 | `accept()` | 연결 수락 | **블로킹**. `(conn, addr)` 반환 |
| 5 | `conn.recv(bufsize)` | 데이터 수신 | **블로킹**. bytes 반환 |
| 6 | `conn.sendall(data)` | 응답 송신 | bytes만 가능 |
| 7 | `conn.close()`, `s.close()` | 소켓 닫기 | 각각 닫아야 함 |

## 4. 클라이언트 흐름과 함수

| 순서 | 함수 | 역할 | 비고 |
|---|---|---|---|
| 1 | `socket.socket(AF_INET, SOCK_STREAM)` | 소켓 생성 | |
| 2 | `connect((host, port))` | 서버에 연결 | 서버가 없으면 `ConnectionRefusedError` |
| 3 | `sendall(data)` | 문자열을 encode해서 송신 | |
| 4 | `recv(bufsize)` | 응답 수신 후 decode | **블로킹** |
| 5 | `close()` | 소켓 닫기 | |

- 클라이언트는 `bind`/`listen`/`accept`를 쓰지 않음. 클라이언트 포트는 OS가 임의 배정(접속할 때마다 달라짐)

## 5. 서버와 클라이언트의 대응

| 서버 | 클라이언트 |
|---|---|
| `bind` + `listen` + `accept` | `connect` |
| `recv` (먼저 받음) | `sendall` (먼저 보냄) |
| `sendall` (응답) | `recv` (응답 대기) |

- 송수신 순서가 서로 반대여야 함. 양쪽이 동시에 `recv`만 하면 서로 기다리며 멈춤

## 6. 헷갈렸던 점 정리

### bind vs listen vs accept
| 함수 | 역할 | 비유 |
|---|---|---|
| `bind` | 소켓에 주소(IP:포트)를 묶음 | 가게 주소를 정함 |
| `listen` | 연결 요청을 받는 상태로 전환 | 가게 문을 열고 영업 시작 |
| `accept` | 들어온 연결을 실제로 수락 | 손님을 안으로 안내 |

- `bind`만으로는 접속이 되지 않음. `listen` 이후부터 OS가 요청을 받음
- 서버가 `bind`하는 이유: 클라이언트가 찾아올 고정 주소가 필요해서
- 클라이언트는 서버를 찾아가는 쪽이라 `bind`가 필요 없음

### bufsize
- `recv(bufsize)`에만 필요한 인자 (`sendall`은 보낼 bytes를 인자로 받음)
- 최대값일 뿐, 정확히 그만큼 오는 게 아니라 도착한 만큼만 반환됨
- **위치 인자만** 받음. `recv(bufsize=1024)`는 `TypeError`

### send vs sendall
- `send`: 보낸 만큼만 처리하고 실제 전송 바이트 수를 반환. 일부만 보낼 수 있음
- `sendall`: 전부 보낼 때까지 반복. 학습용은 이쪽이 안전

### 문자열 ↔ 바이트
- 네트워크는 bytes만 전달하므로 보낼 때 `encode("utf-8")`, 받을 때 `decode("utf-8")`
- 양쪽 인코딩이 같아야 한글이 깨지지 않음
- UTF-8에서 한글은 글자당 3바이트 (서버 출력 `b'\xed\x81\xb4...'`로 확인)

## 7. 오늘 만난 오류와 원인

| 증상 | 원인 | 해결 |
|---|---|---|
| 서버: `recv() takes no keyword arguments` | `recv(bufsize=1024)`처럼 키워드 인자 사용 | `recv(1024)` |
| 서버: `recv() takes at least 1 argument` | `bufsize` 생략 | `recv(1024)` |
| 클라이언트: `ConnectionResetError (WinError 10054)` | 서버가 오류로 종료되면서 읽지 않은 데이터가 남아 RST 전송 | 서버 로그의 원인 오류를 수정 |
| `s.recv(...)` 사용 | `s`는 리스닝 소켓이라 송수신 대상이 아님 | 송수신은 `conn`으로 |

- **디버깅 팁**: 한쪽 오류가 다른 쪽에서는 다른 오류로 보임. 클라이언트에서 `ConnectionResetError`를 보면 서버 터미널 로그를 먼저 확인
- 클라이언트의 `sendall` 성공은 "OS 버퍼에 넣었다"는 뜻이지, 서버가 읽었다는 뜻이 아님

## 8. 코드 점검 메모
- `receive_message != ""`는 bytes와 str 비교라 항상 참. 빈 응답 확인은 `if receive_message:` 또는 `b""`와 비교
- f-string 안에 같은 따옴표를 쓰는 문법은 Python 3.12 이상에서만 동작
- 변수명 `address`(서버 자신의 주소)와 `addr`(접속한 클라이언트 주소)가 비슷해 헷갈릴 수 있음

## 9. 한 줄 요약
> 서버는 `bind`로 주소를 정하고 `listen`으로 문을 열어 `accept`로 손님(연결)을 받으며, 클라이언트는 `connect`로 찾아가고, 둘은 bytes로 데이터를 주고받는다. `accept`와 `recv`는 상대가 올 때까지 기다리는 블로킹 함수다.
